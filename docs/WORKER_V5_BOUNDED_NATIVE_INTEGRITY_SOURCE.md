# Worker V5 bounded native consistency successor

This is a SOURCE-only successor to `4e4bc53accc1cee4a2bfc3eb11124baa0ca5f4d6`. The original first native run retained one failed zero-File constructor case and one unrun nonempty case. Its private original response reported `D1_ERROR: out of memory: SQLITE_NOMEM` during construction. Root rebuilt only the same original esbuild bundle and confirmed the exact failing statement was whole-schema `PRAGMA quick_check`. The failure is preserved, not relabelled as a later pass.

The installed workerd SQLite compiler ceiling and existing remedy are documented in `FP4_RESEARCH_PACKAGES.md` and implemented by `worker/files/jobs/r2-profile-migration-workerd.test.ts`. This successor uses sequential native `quick_check(table)` for every table admitted by the exact V28 application/platform catalog, including `sqlite_schema`, present ledger and SQLite sequence tables. Only the two exactly reviewed Cloudflare platform tables are omitted from native partial checks. Each operation checks its one exact `ok` result. Exact application-table/catalog coverage, whole foreign-key checks, all typed rows/cells/int64 rowids, local singleton/default checks, source/binding/current-owner fences, first-Promise ownership, the code-owned migration ledger and existing construction budget are preserved.

Table checks include their table/index B-trees and constraint checks, but do not establish cross-table page ownership or unused-page coverage. The original two-case qualification therefore joins all native operations and obtains the owned Miniflare disposal acknowledgement before opening each of the two exact persisted original D1 files with `DatabaseSync` in read-only mode. Whole `quick_check` and foreign-key checks then include platform/global coverage. The files are identified by the source/destination installation IDs read from the original native operation. Exact main-file, WAL and SHM inventory and physical path/inode identities must remain unchanged across the read-only checks. Main-file and WAL sizes and SHA-256 remain byte-identical. SHM contains ephemeral WAL reader-lock/read-mark coordination; both its original and observed hashes/sizes are recorded in a private receipt without asserting byte equality or calling the reader coordination a durable-data modification. This is a closed original native-file inspection, not an expected-schema reconstruction or a host D1 adapter.
