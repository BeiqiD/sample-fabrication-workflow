# RT3 provider opening foundation

This slice extracts the existing `openShadowProfile` primary SQL lookup and lifecycle fencing into a neutral `openStorageProfile` capability. The Cloudflare entry keeps its public API and concrete R2, SWITCHdrive and S3 opening paths, including their exact namespace checks, registered runtime state, credential/binding guards and per-request authority. The core uses the existing `JobSqlDatabase` read surface and injected hash/byte contracts; it imports neither Cloudflare bindings nor Node implementation code.

The captured profile ID, revision, namespace and adapter must match the provider result. The returned descriptor is owned and frozen. Read access omits writer/deleter capabilities. Runtime identity, abort state and exact caller authorization are checked around the asynchronous boundaries. Lifecycle functions and each operation's method/key are captured before awaiting caller code, so a pending DELETE cannot turn into a different request and skip its deletion claim.

The trusted provider composer still owns adapter-specific persisted admission and applies the supplied fence immediately before each byte operation. The common core does not register profiles, select defaults, admit File publication, decide retention, retry writes, clean staging, or open another provider on failure. A generic adapter parameter allows a later Node composer to inject an actual local byte adapter without inventing an R2 binding. It does not add `local` to the application's profile/settings/job unions or compose a local application provider.

Qualification used a private archive of `2c5911e69a757c7e9dff03e776ae49a615ab0442` plus the four accepted RT3 byte adapter files. On 2026-10-10, the focused five-file suite passed **82/82** cases: 19 new opening tests and 63 existing Cloudflare profile/R2/S3 tests. The new Node cases use actual file-backed SQLite and actual native local byte writes, independent SHA-256 readback and deletion. They deliberately use small fixture-only authority/admission tables; they do not qualify the current migrated application schema for local profiles. The temporary fixtures use `/tmp` and make no disk-durability claim.

Commands were `npx vitest run server/storage/profile-opening.test.ts worker/files/shadow-profile.test.ts worker/files/r2-profile-bindings.test.ts worker/storage/native-s3-byte-storage.test.ts worker/storage/native-s3-byte-reader.test.ts --maxWorkers 1`, `npx tsc -p tsconfig.server.json`, and `npx tsc -p tsconfig.worker.json`. Existing case deadlines were unchanged. A deliberate mutation removing the operation snapshot made the pending DELETE claim test fail; restoring the implementation passed all 19 new cases in 84 ms. The final Node type graph includes the neutral core and excludes DOM and Cloudflare declarations. Root integration/full gates remain separate.

The current schema through migration 0022/current V24 still accepts only `r2`, `switchdrive`, and `s3`. `storage_profiles` couples each adapter to its configuration source and credentials, with immutable revision 1 and namespace identity. `system_storage_profiles` and its native admission/activation/binding tables describe credentialed S3 candidates; local storage must not masquerade as one. Current role policy, native asset aliases, accepted result publication, job transports and recovery destination mapping also have explicit provider restrictions.

The reviewed current schema inventory identifies 50 adapter-sensitive installed objects: five tables, 43 triggers and two views. This is a review inventory, not an instruction to change every historical guard. In particular, `storage_profile_runtime_legacy_update_guard` selects profiles that are not S3, while `file_locations_native_admission_guard` singles out S3. Adding a local enum alone would inherit an inappropriate legacy branch or skip a native admission fence. Legacy R2/SWITCHdrive locator and retention rules must stay explicit historical rules.

The central reservation was subsequently narrowed: 0023/V25 pairs stable local identity and exact Node installation-ledger/inert recovery policy. Local profile admission moves to the later 0024/V26 package, which must coherently pair profile schema, exact admission/activation/binding identity, role/ingress/publication/GC/job handling, export and protected recovery projections, trusted target DDL/ledger, and installation recovery fencing. Current `target-files.ts` and `target-import.ts` accept only R2/S3 destinations, and frozen V19–V24 export/recovery validation must not silently accept a wider schema. No such DDL/checkpoint or application activation is included in this opening foundation. The proposed local physical identity is `{kind:"local",volumeId,rootId,profileId,namespaceRevision}`, excluding a host path; any eventual canonical format remains subject to the paired schema and recovery review.
