# Portable application runtime implementation plan

Status: **source-informed implementation plan; no Node application, local-profile or Docker support is qualified by this document**.

Inspected on 2026-10-10 at development checkpoint `45c17a9633973ec43a78963dced19e7c2f99175b`. This planning task ran no test commands, changed no application source and provisioned no infrastructure. Filenames described as new below are proposed implementation locations, not existing runnable commands or delivered features.

The [Product roadmap](PRODUCT_ROADMAP.md#portability-and-docker-distribution) schedules complete Node/SQLite/local-volume distribution, followed by small-group resource authorization. The owner's [autonomous development goal](ROADMAP_AUTONOMOUS_DEVELOPMENT_GOAL.md) permits independent development and local qualification while live Phase 6B evidence is unavailable. That permits the six bounded slices below; it does not waive the accepted integrated-tree gate, declare a production release, or change `main`. Group membership and domain-root sharing remain the following milestone, not an excuse to leave this runtime's authentication disabled.

Full Node support therefore requires a reviewed capability migration across every mounted route group, not just a new HTTP listener around `worker.fetch`. ## Conservative implementation defaults

These defaults can be used for local prototypes without asking the owner to select infrastructure. Each becomes an explicit, tested configuration contract before release.

- Use the existing Node 24 baseline, `node:sqlite`, Node crypto/filesystem/HTTP modules and installed Hono. Add no ORM, PostgreSQL, Redis, distributed queue or second domain implementation. Start with one application process and a bounded SQLite connection model; diagnose event-loop blocking before introducing additional worker threads or connections.
- Initial prototype listeners bind loopback. Unauthenticated development mode stays explicitly development-only and retains its current denial of administration. The supported server distribution requires local login; public binding requires configured TLS or a trusted TLS proxy and its reviewed host/proxy policy.
- Provision one persistent local profile for both `internal` and `originals`. External provider credentials are optional. Never silently redirect an unavailable recorded location or selected write destination to local storage.
- Persist an installation manifest, volume identity, database, object root and independently protected encryption keyring. Missing identity/key material for an existing installation fails closed; startup must not regenerate it or reset role defaults. A display name, hostname, absolute mount path or `ASSETS` label does not identify a physical namespace.
- Local-account bootstrap uses an operator-controlled offline action, never the first web visitor. Imported actor strings never create accounts or grants. Keep current administrator permission separate from ordinary authenticated access and future resource-sharing policy.
- Carry existing published size, lease, grace, attempt, retention and step limits into the Node composition. File jobs currently cap 100 Files, 100 MiB per File and five attempts, with a 60-second step/120-second advertised cadence. System recovery currently caps a 100 MiB archive and 60-second steps. Runtime measurements may lead to a reviewed limit change; a faster local disk alone does not authorize raising them.
- Initial local storage assumes an operator-provisioned, server-owned filesystem root on a qualified local filesystem. Network volumes, multiple writers and arbitrary host filesystem mutation remain unsupported until their atomicity/locking assumptions are measured.

## Six implementation slices

### RT1 — One application composition and explicit platform capabilities

Proposed new files: `worker/application.ts`, `worker/runtime/capabilities.ts`, `worker/runtime/sql.ts`, `worker/runtime/cloudflare.ts`, `server/config.ts`, `server/http.ts`, `server/application.ts`, `server/runtime-composition.test.ts`, `server/http.test.ts`.

Extract the existing Hono route registration into an application factory without changing route order, request guards, publication admission, maintenance access or error behavior. Define the smallest actually consumed SQL result/statement surface and explicit identity, storage-opening, hashing, clock/id and background-execution capabilities. Keep Cloudflare bindings in the Cloudflare composer/entry. Hono application bindings must describe application capabilities, not hide `R2Bucket` inside a renamed `Env`. Preserve `JobSqlDatabase` as an existing consumer of the SQL implementation rather than create another File repository.

Migrate consumers in reviewed route-group batches: platform/authentication and storage settings; Samples/execution/verification/definitions; comments/attachments/imports; Projects/references/exports; File/package/recovery services. Every batch uses the same business services and preserves Worker qualification. Existing legacy routes need an explicit adapter for their legacy locations; local storage must not be labeled R2 to keep those routes compiling.

The Node HTTP boundary translates real incoming requests to Fetch requests, streams responses with backpressure, propagates client disconnects, rejects oversized bodies/headers and applies bounded request timeouts. Preserve endpoint-specific limits even when Content-Length is absent or dishonest. Handle streaming request construction explicitly; do not buffer unbounded bodies or reinterpret arbitrary proxy headers as trusted request origin. The frontend/static boundary serves only the reviewed build directory with safe path resolution and SPA fallback after API dispatch.

Finite exit: application route/middleware ownership has one implementation, a loopback Node HTTP prototype runs through it, and actual HTTP tests cover health/readiness, protected-request rejection, body-limit/disconnect behavior and static/API separation. Record routes/capabilities still execution-restricted. This prototype is not yet the supported local application, and cannot pass by casting a fake R2 object to satisfy every route.

### RT2 — Production SQLite adapter and installation migrations

Proposed new files: `server/sqlite.ts`, `server/migrations.ts`, `server/sqlite.test.ts`, `server/migrations.test.ts`, `server/sqlite-contention.test.ts`. Reuse/refine `scripts/lib/file-job-node-runtime.ts`; it must consume the same SQLite capability rather than retain a divergent implementation.

Open file-backed `DatabaseSync` with foreign keys enabled, extension loading disabled, WAL and a bounded busy timeout. The existing File runner's five-second busy timeout is a starting candidate, not a measured application latency promise. Tag prepared statements with their connection owner; reject foreign statements, unsupported bindings and unsafe result coercions. Atomic batches use one synchronous transaction and return the exact consumed `success`, results and change metadata. Qualify `INSERT/UPDATE ... RETURNING`, trigger side effects, guarded zero-row updates, uniqueness/foreign-key failures and rollback after a late statement fails. Establish real D1 versus SQLite metadata behavior instead of copying the test adapter's `total_changes()` approximation blindly.

Authoritative reconciliation reads use the actual current writer connection/committed state. Preserve integer/BLOB/null/text types; represent large rowids/integer evidence with the current exact decimal encoding where required rather than round through JavaScript Number. Object/network I/O remains outside SQL transactions. An async caller must not hold a write transaction across an awaited provider operation.

Installation migrations apply code-owned ordered SQL and record reviewed name/digest/status under an exclusive migration window. Startup refuses mismatched, missing, partially applied or newer unsupported schema. Define platform-local migration-ledger admission in current snapshot/recovery tooling; a new Node bookkeeping table must not accidentally enter a canonical application fingerprint or be silently ignored by an old reader. Schema-changing work includes the required paired current checkpoint. Never remove or rewrite applied historical migrations.

Finite exit: fresh and populated isolated databases run the actual API adapter, migration/restart identities persist, two-process contention remains bounded, a committed-write/lost-HTTP-response case reconciles from a fresh read, and existing optimistic `409` behavior is retained. Qualify WAL-consistent backups/shutdown; copying an open main SQLite file without its WAL is not a recovery strategy.

### RT3 — Registered persistent local bytes and paired File/recovery contracts

Proposed new files: `server/storage/local-profile.ts`, `server/storage/local-byte-storage.ts`, `server/storage/node-sha256.ts`, `server/storage/local-byte-storage.test.ts`, `server/storage/local-profile.test.ts`, `server/local-ingress.test.ts`. Add the next available ordered local-profile migration and its paired current export/recovery checkpoint, choosing their numbers against the accepted tree when implementation begins.

Extend current profile/settings/job unions, validation, immutable namespace constraints and provider-specific trigger guards for an actual `local` adapter. Update the concrete selection/opening paths in `worker/files/shadow-profile.ts`, storage-role policy/current settings, active ingress, GC, migration/package jobs and recovery destination planning through the new capability boundary. Ordinary legacy R2 locators stay R2; they require a mapped readable historical provider or explicit migration, not reinterpretation as disk keys.

A trusted deployment binding maps a registered profile/revision to an exact volume marker and root/prefix. Namespace identity includes a durable opaque volume identity and logical root identity; mounting that same volume elsewhere does not make a new provider, while a different volume/root cannot inherit historical locations merely because its path string matches. Both roles get the same provisioned local profile once, with guarded persistent initialization. Changing a role affects new acceptances only.

Treat logical object keys as opaque identities. Map them to generated physical names, for example an exact profile/key digest with identity-checked metadata; do not normalize traversal-looking strings into another key or concatenate request paths into filesystem paths. Reject malformed/NUL/noncanonical text at the contract boundary. Use a server-owned root, restrictive creation modes, exclusive staging files, no-follow regular-file opens and verified directory/volume markers. Reject symlink/unsupported-link roots and objects. Qualify the supported filesystem's rename/link/fsync semantics and state the limit: application checks do not defend against a host administrator replacing the mount during an operation.

Stream into a unique staging key with incremental source size/hash checks, publish atomically only after complete bytes, and independently read/hash the destination before File publication. Byte metadata/ETags are not hash proof. Keep durable attempts registered before I/O. A write exception after atomic publication is an unknown ACK; reconcile the exact immutable attempt key rather than blindly overwrite/retry/delete. Enable `atomicSinglePut` only after demonstrating this local adapter's complete visibility and reconciliation semantics. Deletion follows the existing authorized claim/hold/grace checks; it does not cancel outstanding writes or authorize key reuse.

Finite exit: real HTTP uploads/comments/diagrams/originals/imports download exact bytes from the persisted local profile, survive restart/default changes, and keep File/occurrence/content-hash distinctions. Actual file-backed schema/trigger/retention cases and non-empty new-checkpoint export/restore pass on SQLite and local workerd where supported. A Worker encountering a local profile reports an explicit unavailable capability unless recovery maps it to a provisioned supported provider; it never tries to access server disk. V19–V24 remain byte/behavior compatible.

### RT4 — Local identity, administrator bootstrap, sessions and secret lifecycle

Proposed new files: `server/auth/accounts.ts`, `server/auth/passwords.ts`, `server/auth/sessions.ts`, `server/auth/bootstrap.ts`, `server/auth/routes.ts`, `server/auth/authentication.test.ts`, `server/auth/bootstrap.test.ts`, `server/auth/session-recovery.test.ts`, `src/pages/LoginPage.tsx`, `src/local-login.mount.test.tsx` and an operator bootstrap entry under `scripts/`. Every new identity/settings table is classified in the paired current export/recovery schema before writes are enabled.

Use stable internal principal IDs while retaining historical Access email as actor provenance. Define the explicit mapping from the authenticated principal to existing actor fields; do not rewrite historical audit attribution or make an arbitrary client-supplied email privileged. Local bootstrap creates/grants the initial administrator through a deployment-owned offline operation. An existing installation cannot create another first administrator by deleting a cookie or visiting a setup route.

Use salted, versioned password hashing with Node crypto. A conservative scrypt candidate is `N=2^17`, `r=8`, `p=1` with a separately bounded memory/concurrency budget; measure it before selecting the shipped parameters, persist them per verifier, and never silently weaken them when the configured runtime cannot support them. Store only password verifiers and hashed high-entropy session tokens. Apply explicit absolute/idle expiry, login throttling, session rotation/revocation, HttpOnly/SameSite cookies, Secure cookies for supported public HTTPS operation and same-origin/CSRF validation for cookie-authenticated mutations. A loopback HTTP development exception must be explicit and cannot authorize a public insecure listener.

Refactor administrator, ordinary-access and File-evidence operator checks to consume genuine current capabilities for Access or local principals. Background acceptance, step execution/publication and output download recheck current permission; old sessions, recovered actor claims and imported packages are not grants. No membership/workspace schema is added merely to implement local login.

Load the existing storage-credential envelope keyring from a separately provisioned private file or equivalent deployment secret. Reuse its AES-GCM identity/AAD/version semantics; preserve old keys while any retained payload/check snapshot/protected backup needs them. Missing/wrong keys disable credential-dependent operations without resetting configuration. Provide an offline, audited account-recovery action under a stopped/fenced writer that revokes sessions; do not depend on an email service for the first individual-user distribution.

Finite exit: the actual Node application authenticates users and denies unauthorized administrator actions, rejects session fixation/forgery/expired/revoked sessions and cross-origin writes, and preserves stable identity across restart. Protected recovery preserves account identity/verifier material only under its reviewed policy and leaves sessions, active grants and execution inert until destination bootstrap explicitly restores authority. Portable research packages exclude those credentials/grants entirely.

### RT5 — Restartable jobs, local assisted recovery and cross-runtime rehearsal

Proposed new files: `server/jobs/runtime.ts`, `server/jobs/package-capabilities.ts`, `server/jobs/recovery-capabilities.ts`, `server/recovery/target.ts`, `server/recovery/artifact-store.ts`, `server/jobs/restart.test.ts`, `server/jobs/fencing.test.ts`, `server/recovery/assisted-recovery.test.ts`, `server/recovery/cross-runtime.test.ts`.

Compose existing File, package and system-recovery kernels/repositories through the real SQLite/local-storage/hash/auth capabilities. Extract format/domain portions of the current Worker package/recovery composition once for both runtimes. Private system-backup artifacts receive an exact installation-owned local namespace and private keys; replace the hard `ASSETS`/R2 assumption through an explicit artifact-store capability, retaining its frozen namespace and authorized download checks.

Use a bounded fair local dispatcher with the existing advertised cadence and one current durable action per slot, cancellation on shutdown, lease/incarnation/owner/generation fences and separately authorized cleanup. A process restart reconnects to the persisted incarnation/state; it does not issue a fresh enable operation on every boot or replay paused work. Restored targets remain disabled. Preserve `enableNodeFileJobs`' explicit reconfiguration semantics and per-job resume requirement instead of treating the runner's `--enable` as an automatic startup option.

Local assisted restore writes to a fresh isolated database and object namespace, checks canonical rows/typed cells/File bytes/content hashes, then reports readiness without replacing the live source automatically. Planned cutover fences and drains source writers, validates the frozen checkpoint again, shuts down/checkpoints the source database and activates the reviewed database/root/process binding together. Historical recovery explicitly identifies loss after its recovery point. Retain the old source read-only; after destination writes begin, returning to it requires reconciliation rather than an automatic rollback.

Finite exit: independent Node processes resume actual migration/package/recovery work, unknown ACKs reconcile without duplicate publication, revocation/timeout/reclaim fences prevent late publication, snapshot holds protect source bytes, and clean restart exposes exactly the accepted results. Non-empty local workerd D1/R2 ↔ Node/SQLite/local package copy-import and identity-preserving backup recovery pass with explicit physical mappings and protected capabilities inert. This qualifies the exercised local runtime pairs, not an authenticated deployed Cloudflare ↔ Docker transfer.

### RT6 — Container distribution, persistent upgrade and operator handoff

Proposed new files: `vite.node.config.ts`, `scripts/build-node.mjs`, `server/main.ts`, `Dockerfile`, `.dockerignore`, `compose.yaml`, `scripts/verify-node-distribution.mjs`, `server/distribution.test.ts`, `docs/NODE_DEPLOYMENT.md`, `docs/NODE_RECOVERY_RUNBOOK.md`. Add corresponding package scripts only when their implementation exists; the proposed names here are not current executable commands.

Build the same frontend without generating Cloudflare bindings and bundle the Node entry with explicit externals. Produce a pinned, supported Node 24 image running as a non-root user, with a read-only image filesystem, bounded transient scratch and separately mounted persistent database/object/installation-state volumes and protected secret input. Never bake account credentials, storage keyrings or populated databases into an image. Health/readiness use the real application and fail meaningfully for an incompatible schema; an optional historical provider outage must not pretend the entire database is unavailable.

Document first bootstrap, volume ownership/permissions, TLS/proxy settings, restart, safe migration windows, key backup/rotation, account recovery, bounded job execution and fresh-target restore. Qualification must recreate the container/process against the same volumes, upgrade a populated prior supported version, reject an incompatible downgrade and prove that default/profile/installation identities and accepted jobs are retained. Recovery includes both the database and bytes plus independent bootstrap secrets. Restoring an image alone is not recovering an installation.

Finite exit: a real built image/container completes the enabled application flows and volume/upgrade/fault matrix, with exact source/image digests and retained reports. If no usable container engine is available, finish the Node bundle, Docker sources and non-container checks, record the unexecuted image/container gate and keep support restricted. An actual private Cloudflare ↔ deployed-container non-empty recovery/import rehearsal remains an external acceptance gate requiring both runnable authorized deployments; it cannot be inferred from host tests or image construction.

## Required fault and acceptance matrix

| Boundary | Concrete injection | Expected result | First coverage |
| --- | --- | --- | --- |
| HTTP owner | Disconnect during request upload/response stream; incorrect/missing Content-Length; unsafe encoded static path | Bounded cancellation/body rejection; no API/static routing confusion or escape from the build root | RT1 |
| SQL publication | Fail a later statement after guarded mutation; concurrent revision change; commit before response loss; unsafe integer/BLOB round trip | Entire batch rolls back or authoritative receipt proves the commit; explicit conflicts and exact cells | RT2 |
| Migration/restart | Populated schema upgrade, interrupted migration, foreign statement, live WAL, newer schema | Reviewed atomic/identified state, no startup reset, no unsupported automatic downgrade | RT2 |
| Local namespace | Change default/root mapping/volume marker during accepted write; symlink/link object; `../`, encoded separators, NUL or colliding normalized keys | Original exact namespace/key persists or fails unavailable; no fallback/path escape/reinterpreted identity | RT3 |
| Byte outcome | Disk full/truncated source/corrupt destination; rename committed then ACK lost; kill process before/after publish | No unverified File publication; exact attempt survives and is reconciled; no destructive automatic retry | RT3 |
| Authorization | Login/session replay, bootstrap repeat, forged actor, admin revocation during job/download, recovered account/grant | Verified current principal only; original actor retained as provenance; recovered capabilities remain inert | RT4 |
| Secret retention | Missing/wrong keyring, rotation with old retained envelopes, restart without credential re-entry | No reset/plaintext leak; historical keys retained until independently proven unnecessary | RT4 |
| Provider egress | Redirect/private-address/IPv6-mapped/changed-DNS destination for optional S3/WebDAV transport | Deployment-owned policy and transport prevent unauthorized egress before sending credentials; unsupported cases fail unavailable | RT3 adapter, RT5 job |
| Executor | Kill/restart, expired lease, pause/reclaim while I/O held, late atomic write, shutdown during cleanup | Durable owner/incarnation fences, separately authorized cleanup and no stale publication/replay | RT5 |
| Recovery | Source/target alias, same-root target, changed source checkpoint, malicious/partial archive, rollback before versus after target writes | Isolated target, code-owned DDL, verified identity/bytes, explicit cutover/loss boundary and no live-source deletion | RT5 |
| Distribution | Recreate container with existing volumes, populated upgrade, mismatched image/schema, absent secret/volume, non-root permissions | Persistent identities/defaults, deliberate failure instead of creating a new installation, exact image/source receipts | RT6 |

These are required outcomes, not tests already run. Use actual Node HTTP, file-backed SQLite and disk I/O for the runtime qualification, with controlled faults and independent process restarts. Mocks can test narrow policy branches but cannot replace this matrix.

Optional external transports need their own Node capability check. Current metadata rejects obvious unsafe endpoints, but a hostname string check alone does not qualify Node SSRF protection. Resolve and validate the effective destination at the transport boundary, address DNS rebinding and redirects, preserve TLS verification and reviewed trusted proxy policy, and do not send credentials to an unqualified target. If pinned/validated transport cannot be supplied, keep that optional provider unavailable while local storage remains useful. The existing S3-compatible label is not evidence of provider checksum, multipart, visibility or atomicity equivalence.

## Qualification records and work that can continue independently

Existing repository commands available for relevant regression gates include `npm run test:source`, `npm run test:reference-mounted`, `npm run typecheck:file-jobs-node`, `node --test scripts/fp3-node-runner.test.mjs`, `npm run verify:d1-migrations`, `npm run verify:ci` and `npm run build`. They were inspected in `package.json`/the runner sources; **none was run by this planning task**. Existing build/gates qualify their current targets and do not substitute for the future Node/container checks.

For each implemented slice record its accepted source/tree identity, actual command and exit/count, filesystem/runtime configuration and explicit injected faults. Record complete, failed, interrupted, skipped and unexecuted checks separately. Keep sample credentials and raw account/session/key material out of receipts. Do not claim a future script, image, provider or remote gate passed because its plan has been written.

RT1–RT5 can progress with isolated local fixtures, generated test identities/keyrings and the existing local workerd harness, without Cloudflare Access credentials or live provider accounts. RT6's Node/package/container-source work can likewise proceed independently. Missing authenticated test access, a real container engine, real provider credentials or deployed physical-volume evidence blocks the corresponding acceptance only; it must not stop unrelated prototype implementation or be silently replaced by a mock pass.

Completion of this milestone requires all enabled RT1–RT6 exits and an explicit supported/disabled capability matrix. Production `main`, live deployment activation, real provider activation and source-data cutover remain outside this development-only plan. The following small-group milestone then supplies membership/domain-root permissions end to end; this document does not mark that work complete or enlarge it into distributed tenancy.
